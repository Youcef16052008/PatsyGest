**Scope checked:** the supplied Google Drive folder, the review/reproduction artifacts discoverable in the connected Drive, and the current checkout at `2fba72c` (`arena/d51c48b6-patsygest`). This is an evidence review and implementation plan; no application or database changes are made in this document.

## Executive decision

**Do not treat the review reports as one undifferentiated list, and do not deploy their proposed patch wholesale.** The artifacts contain several reproducible defects, some product/requirements questions, and at least one finding whose “security vulnerability” label does not match the code’s stated threat model. Phase 0 has now compared the checked-out branch with the current deployed metadata: the live Supabase order RPC has been corrected (D3), but that fix is not present in this branch’s SQL; R1 is fixed in current upstream `main`, not in this branch. The highest confirmed outstanding risks are cross-tenant restore/reference validation (D7), direct site/plan-column writes (D4/D9), POS/SQL rounding mismatch (R2), UTC business dates (R5), and the exact-cap export/backup failures (R4/R4b). See `PHASE-0-EXECUTION.md` for the read-only environment evidence and branch-vs-deployment status.
The supplied folder itself is not a collection of review reports: it lists five similarly named `FRG` folders containing source-tree snapshots. Drive search also surfaced separate review/reproduction artifacts outside that folder. I assessed those artifacts below; if the five snapshots represent separate agent branches/reviews, their actual written reports or a clearer index are still needed before claiming every agent review has been covered.

The checked-out app’s existing unit suite passes (**366/366**, run during this review), but it does not exercise most of the reported failure scenarios. A green suite therefore does not refute the findings. The separate Drive harness reports 11/20 passing before its patch and 20/20 after its patch; that is useful evidence, but it is a fake-Supabase/`next start` harness, not proof against the live pilot or production database.

## Finding-by-finding assessment

| ID | Assessment | Priority | Basis / qualification |
|---|---|---:|---|
| R1 — CSV JSON/JSONB values become `[object Object]` | **Confirmed** | P1 | `cellule()` stringifies ordinary objects with `String()` and joins arrays directly. My local source execution returned `[object Object]` for both an object and an array of objects. Sale-line JSON and other nested JSON exports are therefore not round-trippable/readable. `src/lib/csv.ts:35-46`. |
| R2 / D1 — POS display rounding differs from SQL numeric rounding | **Confirmed** | P0/P1 | Browser code rounds IEEE-754 numbers; SQL rounds `numeric` (half away from zero). For 1 unit at 2.50 HT and 19% VAT, browser code returns 2.97 while exact decimal half-up/SQL gives 2.98. SQL uses `round(..., 2)` in `supabase/21-prix-demain-panier.sql:472-475`; browser calculation is at `src/lib/pos-cart.ts:167-184`. The supplied audit reports 4,715 mismatches across 200,000 combinations. Must independently add an automated test for that full matrix. |
| R3 — app paths on a shop subdomain are rewritten to the storefront | **Behavior confirmed; bug status depends on product intent** | P2 / decision | Local execution confirms `/caisse`, `/stocks`, `/production`, `/rejoindre`, and `/estimation` all rewrite to `/vitrine/<slug>`; `/connexion` is not rewritten. `src/lib/domaines.ts:110-122,129-168`. This is also explicitly the current implementation’s documented rule (“all paths except allowlisted app paths”). The report’s expected behavior—back-office routes remain available at the shop host—is not proven to be a requirement. Decide the intended hostname/path contract before changing it. |
| R4 — export fails exactly at its row ceiling | **Confirmed** | P1 | `api/export` reads offsets only while `< 20000`; a full final page leaves `complete=false`, and returns 500. The supplied HTTP harness reproduces 19,999 rows succeeding and 20,000 failing. `src/app/api/export/route.ts:37-49`. |
| R4b / BUG-002b — backup fails at its 50,000-row table ceiling | **Confirmed** | P1 | Same off-by-one/probe issue in `src/app/api/sauvegarde/route.ts:38-62`; at exactly 50,000 rows it reports incomplete before the size check. The provided harness reproduces it. Keep backup fail-closed—never return a truncated archive as complete. |
| R5 — UTC date is used as the Algerian business date | **Confirmed for Algeria-local business operations** | P1 | At `2026-03-10T23:30:00Z`, local `Africa/Algiers` date is March 11 but UTC date is March 10. `importZReal` rejects any date later than UTC “today” (`src/lib/actions-caisse.ts:257`); thus a valid current-day Z can be rejected around local midnight. The same date pattern appears in many business forms/helpers, so a one-line Z-only patch would be incomplete. |
| R6 — inherited object keys pass the demo-account check | **Confirmed input-validation bug; impact is limited** | P3 | `PILOT_ACCOUNTS` is a plain object and the login guard uses truthiness (`src/lib/actions-auth.ts:29-35`); `constructor` and `__proto__` resolve through the prototype. Local execution confirmed both lookups truthy. `demoEnabled()` explicitly excludes production (`src/lib/auth.ts`), and spreading the `constructor` result yields no account fields, so this is not evidence of a production account takeover. Still fix with an own-property allowlist and test it. |
| R7 — 32-bit FNV fingerprint is forgeable | **Not a vulnerability under the documented design** | P3 / threat-model note | `src/lib/sauvegarde.ts:112-124` explicitly says this detects accidental corruption, is not a cryptographic signature, and is not intended to be one. The report’s expectation (“edited file cannot be made valid without a secret”) is stronger than the current contract. If the product requires malicious-tamper evidence, introduce a keyed signature with a managed key and rotation/recovery; otherwise clarify UI/docs that a user can recompute the checksum. This must not be confused with D7, a separate tenant-isolation flaw. |
| D2 — public catalogue exposes `client_id` | **Confirmed exposure; severity overstated if described as a credential leak** | P2 | `vitrine_catalogue` grants `anon` SELECT and selects `p.client_id` (`supabase/26-vitrine-publique.sql:228-255`). It is a stable internal tenant UUID, not an auth token, but it is unnecessary public data and contradicts the nearby claim that no internal identifier is exposed. Remove it from the public projection if no client code needs it; use a non-sensitive public key where necessary. |
| D3 — anonymous storefront order RPC references a missing record field | **Confirmed by source and the supplied DB reproduction** | P0 for storefront launch | In `supabase/27-commandes-vitrine.sql`, `v_site` is populated with `s.id, s.client_id, s.nom`, but later the function reads `v_site.subdomain` when querying `vitrine_catalogue`. A PL/pgSQL `record` has no such field unless selected. The supplied PGlite audit reports every valid submission failing with “record `v_site` has no field `subdomain`.” Existing source-level tests do not detect execution of this path. |
| D3b — global storefront request cap can be exhausted by junk submissions | **Confirmed design weakness; reproduce under current schema before rollout** | P1 | The RPC rate-limits by total tenant orders (`30/hour`), not by source/session or abuse signal. An anonymous caller can consume the tenant’s quota with junk submissions before legitimate customers. The supplied DB scenario demonstrates 30 junk rows blocking a genuine request after applying a one-line D3 fix. Rate-limits need a threat-modelled design; IP storage is not the only option, but a single tenant-wide counter is insufficient. |
| D4 — direct `sites` UPDATE bypasses protected operations | **Confirmed policy/authorization gap** | P0 | Base migration `01-socle.sql` allows `proprietaire` and `labo` to update site rows. Migration 25 reserves names and migration 31 restricts publication to owner-only via RPC, but the original broad UPDATE policy still permits changing those columns directly. The supplied PGlite repro changes a reserved name to `support` and publishes as `labo`. Add column-level/table-grant restrictions or a restrictive policy/trigger so protected fields can only change through validated RPCs; do not rely on UI routing. |
| D5 — older backup format fails against newly required columns | **Confirmed compatibility risk** | P1 | Migration 25 adds `sites.publication text NOT NULL DEFAULT 'aucune'`. Restore uses `jsonb_populate_recordset(null::table, ...)` and inserts records (`supabase/18-restauration-sauvegarde.sql`), so an older dump lacking `publication` supplies NULL rather than the table default. The audit reports a version-1 restore failing the NOT NULL constraint. Version the format and map defaults explicitly or reject old formats with a clear, pre-write error. |
| D6 — a single duplicate row can skip the whole table on restore | **Confirmed data-recovery defect** | P1 | The restore catches `unique_violation` around a bulk table insert and records every row as ignored (`supabase/18-restauration-sauvegarde.sql:141-145`). If only some rows already exist, the statement is rolled back as a unit and genuinely missing rows are not restored, yet the routine returns a result. The current draft `124-restauration-gardes-brouillon.sql` attempts to fail the whole operation on conflicts but is explicitly a **draft**, not approval to deploy. Define restore semantics (all-or-nothing, merge, or idempotent row-wise) and test partial overlap. |
| D7 — restore permits cross-tenant foreign references | **Credible and high-risk; DB-isolation reproduction supplied** | P0 | A `SECURITY DEFINER` restore bypasses normal RLS. The supplied PGlite result restores a tenant-A recipe-family row linked to tenant-B’s article and reports the foreign article price visible through the public catalogue join. Current public view joins articles by product ID only. The draft 124 adds post-insert checks for foreign keys where both tables have `client_id`, but is not deployed, and does not validate every JSON-embedded reference. Reproduce against the exact current migration chain and close every FK/JSON/reference path before any restore is used on real data. |
| D9 — tenant owner can change the subscription plan directly | **Confirmed in the supplied schema/DB reproduction; re-check live ACLs** | P1 | `clients.offre` is an ordinary column (`supabase/01-socle.sql:9-18`); owner UPDATE policy is row-wide. If authenticated has UPDATE privilege—as the audit’s PGlite setup does—the owner can self-upgrade. Enforce plan writes via a platform-controlled role/RPC or column privileges and test with authenticated PostgREST. Verify actual pilot grants before stating live exploitability. |
| D0 — fixture migration sequence applied 29/29 | **Positive evidence, not a defect** | — | Demonstrates the script’s selected historical + storefront fixture sequence applies in its PGlite setup. It does not certify pilot equivalence, the live migration history, or the security behavior of every routine. |
| D8 — only named anonymous RPC is executable | **Positive evidence, not a defect** | — | The audit allow-list result is good evidence for that tested schema snapshot. Keep it as a regression assertion; still test direct table grants, views, and every HTTP/public path. |

### Patch review

The Drive patch is a useful candidate, not a complete remediation. Its 20/20 after-fix result addresses the HTTP harness cases it contains: exact 20,000/50,000 boundaries, 2-second auth delay, selected security headers, unprovisioned-account message, and one module RPC per request. It does **not** cover R1, R2, R3, R5, R6, R7, D2–D9, nor does it prove behavior against a live Supabase/PostgREST deployment. Before applying it, review:

1. Whether the auth timeout change is consistent across `getSessionContext`, proxy refresh, server actions and route handlers (the patch changes `auth.ts`; current proxy still has a separate 1.2-second timeout).
2. Whether the headers match the app’s inline-script, image, hosting and iframe needs; the patch itself defers a strict nonce-based CSP.
3. Whether the 20k/50k probe is unambiguous for an exact cap and over-cap dataset, and whether the export/backup UX states the cap clearly.
4. Whether the React request cache is scoped to a single request as expected and does not memoize identity-dependent data across requests.
5. Add the reproduction tests to the repository rather than relying on external log files.

## Full action plan

### Phase 0 — preserve evidence and establish a safe baseline (before editing SQL)

- [ ] Record the target environments separately: checked-out commit, deployed Vercel commit, Supabase project/migration history, and whether storefront functions/migrations are live. Do not infer current production state from the Drive/PGlite snapshot.
- [ ] Export the current database catalogue read-only: table grants, RLS policies, views and `security_invoker`, function definitions/ACLs, constraints/FKs, and migration history. Compare with the repo using the existing audit queries; do not run experiments on the pilot.
- [ ] Save the external reproductions and logs as referenced review evidence (do not treat the supplied `FRG` snapshots as authoritative baselines until their source commits are identified).
- [ ] Add a reproducible test harness to CI for the newly listed findings. Keep DB/security tests on a disposable Supabase CLI/PGlite environment; no real customer rows.
- [ ] Preserve the current test baseline: `npm test` currently passes 366/366; add new tests first so each fix has a red/green proof.

**Gate:** no behavior-changing SQL is drafted until the live schema/ACL baseline and exact deployment targets are known.

### Phase 1 — block tenant boundary and public write risks (highest priority)

1. **D7 restore isolation.** Inventory every FK and logical/JSON reference for every restorable table. Prefer composite tenant-aware foreign keys where feasible; validate tenant ownership before any SECURITY DEFINER insert. Reject an entire dump before writes if an external reference is present. Cover valid restore, foreign parent IDs, foreign `client_id`, nested JSON references, concurrent mutation, rollback, and conflict behavior. Re-run against a clean, exact migration chain and compare row counts/references after rollback.
2. **D4 site writes.** Remove broad authenticated UPDATE on sensitive site columns. Restrict direct writes to safe fields or deny direct UPDATE and implement narrowly scoped owner/validated RPCs for name/type/address, subdomain, custom domain and publication. Make the DB—not merely the UI—reject reserved names and unauthorized publication. Test owner/labo/vendor direct PostgREST UPDATE and allowed RPCs.
3. **D9 subscription entitlement.** Separate platform billing state from tenant-editable fields. Revoke client UPDATE on `offre`; use a trusted platform-only mechanism. Verify `anon`, `authenticated` owner, service role and platform-admin boundaries in the actual ACL model.
4. **D3/D3b storefront.** Include the required subdomain in the `v_site` record or compare using a selected validated value. Add an end-to-end anonymous PostgREST request test through a published site; assert accepted request, repeat idempotence, unpublished/unknown site refusal, no price control, and no private response data. Replace tenant-global-only flood cap with layered abuse controls that do not let anonymous junk exhaust all legitimate demand; test concurrency and race conditions.
5. **D2 public projection.** Remove `client_id` from the anon view and explicitly enumerate the public response fields. Test the exact anon JSON/REST payload, not only SQL text. Check product ids, image paths and error responses for other internal identifiers.

**Gate:** two-tenant Auth/PostgREST adversarial suite passes; schema constraints and ACLs are verified against the intended deployment snapshot; no restore or public write has an untested cross-tenant path.

### Phase 2 — money, dates and customer data correctness

1. **R2/D1 money.** Choose one canonical rounding contract (prefer exact decimal/integer cents matching SQL). Avoid binary float as the authority; convert submitted price/quantity into validated decimal units or have the server return the authoritative ticket totals before confirmation. Add known half-cent cases (including 2.50 × 1.19), positive/negative boundary behavior if relevant, many lines, quantities and TVA rates, and a generated 200,000-case comparison. Assert the displayed receipt equals the committed DB row and returned RPC values.
2. **R5 timezone.** Define the tenant/business timezone explicitly (`Africa/Algiers` for the current Algeria pilot, or per-tenant configuration). Centralize business-date calculation; audit all `toISOString().slice(0,10)` date paths in forms, Z import, stock, purchasing, sales, production and reporting. Keep UTC timestamps for instants, but compare business dates in the configured timezone. Test 23:00–01:00 UTC boundaries, UTC+1, leap-day and date-only inputs. Ensure SQL `current_date` rules use the same business-date contract.
3. **R1 CSV JSON fidelity.** Define CSV serialization for arrays/objects (stable JSON serialization, with correct CSV quote escaping and formula-injection mitigation). Do not flatten objects as `[object Object]`. Add nested object/array, Unicode, newline, delimiters, quotes, and JSON round-trip expectations. Consider a separate JSON export for complex tables.
4. **D5/D6 backup restore semantics.** Add a dump schema version and explicit migrations/default mappings for older formats. Validate the entire dump and compatibility before writes. Decide whether restore is replacement, append/merge, or idempotent replay; never mark a table fully restored if only part of its rows were inserted. Use per-row deterministic conflict reporting or all-or-nothing rejection, with a transaction and exact counts. Test old version, partially overlapping table, duplicate key in middle, FK-ordering, size limits and transaction rollback.
5. **R4/R4b pagination.** Adopt a tested page protocol: fetch another page when exactly full, distinguish “exactly at cap” from “more than cap,” and return a clear size-limit response instead of 500/incomplete. Verify zero rows, cap−1, cap, cap+1, multiple pages, stable ordering and concurrent inserts/deletes. Never silently truncate or label a partial backup complete.

**Gate:** POS receipt and persisted totals match exactly; business date tests pass at midnight; CSV is lossless for supported types; restore/export boundary tests do not silently omit data.

### Phase 3 — routing, auth resilience and defensive hardening

- [ ] **R3 product decision:** agree whether shop hostnames should serve `/caisse`, `/stocks`, `/production`, `/rejoindre`, and `/estimation`. If yes, explicitly allowlist protected app routes and test signed-in/out behavior; if no, document a canonical app hostname and show a helpful redirect/404 rather than accidentally returning storefront content for every path.
- [ ] **R6 demo login:** use `Object.hasOwn(PILOT_ACCOUNTS, email)` or a `Map`; reject all non-enumerated emails in both login and cookie-to-context resolution. Test `constructor`, `__proto__`, `toString`, mixed case, whitespace and expired/tampered cookies. Keep demo mode non-production only.
- [ ] **R7 backup checksum:** retain FNV only as accidental-corruption detection and make that clear in the UI; do not claim adversarial integrity. If malicious tampering is an actual threat requirement, design a keyed HMAC/signature, key rotation, recovery and compatibility procedure separately. Do not embed a signing secret in the downloadable file or browser.
- [ ] **Drive patch subset:** port suitable fixes for export/backup boundary, authentication latency, security headers, unprovisioned-account UX and request-scoped memoization only after code review. Add committed tests and run build/typecheck/lint plus the isolated Auth/PostgREST suite. Check the separate proxy timeout rather than assuming the `auth.ts` change covers it.
- [ ] Add observability that distinguishes auth service slowness from missing/invalid session without logging secrets or personal customer data.

**Gate:** route behavior is approved, cookies/session tests pass under latency and errors, headers do not break Next or required assets, and CI covers each retained finding.

### Phase 4 — deployment and operational verification

- [ ] Keep all SQL tests on a disposable database. Build migrations as additive, reviewed migrations; never copy/paste draft files 101–128 to a live project based solely on their filenames or the audit results.
- [ ] Produce a migration runbook per environment: preflight query, backup, exact ordered SQL, expected catalogue checks, canary tests, stop conditions and rollback/forward-fix. Reconcile migration history and schema drift before applying.
- [ ] Restore a fresh encrypted backup into an isolated database and verify data counts, tenant references, ACLs/RLS, functions, auth account mapping and Storage assumptions. A checksum or a successful export is not a restore test.
- [ ] Deploy to a truly isolated Preview database first. Run storefront, anonymous abuse limits, two-tenant isolation, owner/labo/vendor direct-write tests, login latency, exports and recovery tests against the deployed build.
- [ ] Only then plan a coordinated production release with an owner-approved maintenance window, reversible app release, post-deploy read-only catalogue check, smoke tests and monitoring. Do not test writes against pilot/customer records.

**Final go/no-go:** no release while D7/D4/D9 or any tenant-boundary test fails; no POS rollout while R2 diverges; no storefront launch while D3/D3b is unaddressed; no claim of a complete backup until D5/D6 and restore drill are closed.

## Immediate next implementation batch

Once the user approves an implementation pass, the recommended sequence is: **(1)** commit regression tests for D3, D4, D7, R2, R4/R4b, R5, R1; **(2)** fix DB authorization/tenant isolation and storefront order behavior in isolated SQL; **(3)** fix money/timezone/data-export/restore semantics; **(4)** take only the relevant fixes from the Drive patch and test them; **(5)** run full CI and an isolated deployment rehearsal. The external patch alone is not enough to close the audit.
