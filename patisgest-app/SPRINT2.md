# Sprint 2 — état du pilote

## Base et comptes

La base du pilote Supabase a été initialisée avec `01-socle.sql`, puis les tables de `03-sprint2-modules.sql`. Le script `02-seed-pilote.sql` crée le client, les sites et trois comptes Auth de **démonstration** (mot de passe connu : `PatisGest2026!`). `04-securite-lecture.sql` retire l'auto-modification des utilisateurs et limite les tables métier Sprint 2 à la lecture par client. `05-ecritures-articles-lots.sql` réintroduit des écritures **sécurisées et testées** pour les articles, les lots et les mouvements (rôles propriétaire + labo uniquement, `with check` strict par client y compris via les clés étrangères, réception atomique par RPC `receptionner_lot`, contrainte de quantité positive, journal des mouvements sans UPDATE/DELETE). Le jeu de données métier ajouté au projet distant n'est pas intégralement inclus dans le script de seed local.

Ces comptes et leur mot de passe sont publics et ne conviennent pas à des données réelles. Désactivez-les ou remplacez leurs identifiants avant utilisation réelle. Les politiques actuelles isolent les clients mais ne restreignent pas encore la lecture des coûts par rôle. Ne pas considérer ce pilote comme prêt pour la production.

## Ce qui fonctionne

- La connexion normale utilise Supabase Auth et les données distantes s'affichent sur les pages Stocks, Achats, Recettes, Production, Planning, Simulation prix, Transferts, Caisse, Clôture, Qualité, Traçabilité et Cake Design.
- **Écritures réelles (Sprint 2, en cours)** : la page Stocks propose la création d'articles et la réception de lots pour les rôles propriétaire et labo ; la page Caisse propose une **vente réelle** pour tous les rôles (le vendeur compris). Les server actions utilisent la session de l'utilisateur : la RLS applique l'isolement par client, les clés étrangères inter-tenant sont refusées, la réception crée lot + mouvement en une transaction, et le journal des mouvements n'accepte ni UPDATE ni DELETE. Les ventes passent uniquement par la RPC `vendre_article` (frontière d'autorisation SECURITY DEFINER testée) : consommation FEFO atomique avec verrouillage des lots, idempotence par ticket unique `(client_id, ticket)`, manques signalés sans stock négatif, vente + mouvements dans une seule transaction. La page Production propose le cycle complet des OF via trois RPC (`creer_of` avec besoins recalculés côté serveur à partir de la version de recette figée, `demarrer_of` consommant les besoins en FEFO sur le site de l'OF, `terminer_of` recevant le lot produit au coût connu) — aucun INSERT/UPDATE direct n'est possible sur `ordres_fabrication`. La page Transferts propose le transfert réel entre sites via la RPC `transferer_article` : FEFO au départ, lots miroirs (même n°, DLC, prix) à l'arrivée, deux mouvements atomiques, stock insuffisant refusé (un transfert ne crée jamais de manque). **Journaux et achats réels (migration 09/10)** : la page Clôture saisit la clôture déclarative six flux via la RPC `saisir_cloture` (lignes enrichies nom/prix depuis l'article, révisions gérées, correction explicite) ; la page Qualité écrit relevés de température, nettoyages et non-conformités en RLS (clôture NC via `maj_non_conformite` avec action corrective obligatoire et historique) ; le Planning écrit les tâches avec bascule « fait » ; Cake Design crée les devis (`creer_cake`, tous les rôles, rétroplanning J-3/J-1/J) et évolue via `evoluer_cake` (acompte 30 %, solde avant livraison, annulation) — aucun INSERT direct n'est possible sur `clotures`, `cakes` ni `bons_commande`. **Import Z sécurisé (migration 11)** : la caisse importe un Z au format strict `code;quantité;prix HT` avec aperçu, la RPC `importer_z` résout chaque code côté serveur (inconnu ou ambigu = refus complet), consomme en FEFO, journalise dans `z_imports` (identifiant date+caisse+n° Z idempotent) et exige la confirmation « import distinct » si un autre Z du jour a le même total HT. Les Achats créent des bons de commande **multi-lignes** (`creer_commande`) et reçoivent partiellement ou totalement (`recevoir_commande`) : création de lots (n° + DLC exigés) + mouvements entrants + lignes d'historique des prix pour l'alerte > 10 %, statut `commande` → `partiel` → `recu`. **Alerte de variation de prix** : chaque réception alimente l'historique ; au-delà de ±10 % entre le dernier et le précédent prix (article + fournisseur), la page Achats affiche une bannière et un indice en ligne à la saisie. **Rapprochement caisse/clôture** : la page Clôture compare (lecture seule) le « vendu » déclaré aux ventes réelles du même jour/site — dernière révision conservée, ventes non déclarées signalées en écart. **Étiquette produit (MOD-10, MVP)** : la page Stocks génère l'étiquette d'un produit fini — ingrédients de la recette active avec allergènes surlignés (14 officiels), allergènes/traces du produit, lot + DLC parmi les lots en stock, impression — valeurs nutritionnelles non fournies (V4). **Sous-recettes & conversions (migration12, MOD-04/D2)** : table `conversions` par tenant (RLS complet), familles créables (`creer_famille`), versions immuables à lignes **article ou sous-recette en version figée** (`creer_version` : conversions exigées à la création, anti-cycle BFS max3, activation unique par famille), et `creer_of` qui **étend récursivement** les sous-recettes avec parage + conversions et fusionne les doublons — la régression seed est exacte. **Traçabilité & rappel (migration13)** : `rappel_lot` (rapport en cascade — ventes, OFs consommateurs, transferts, lots descendants produits/transférés max3, ventes des descendants, lecture tous rôles) + `bloquer_lot` (motif requis, propagation facultative aux descendants, déblocage jamais propagé) avec UI sur le module Traçabilité. **Simulation réelle (modif de comportement)** : `simuler_recette` (wrapper interne → version active + `patisgest_besoins_de_version` : sous-recettes et conversions incluses) + `fefo-cost` (coût FEFO pur JS, ordre identique SQL) + `SimulationForm` sur le module Simulation — la simulation n'est plus « démo locale » : elle calcule sur les opérations réelles (besoins étendus + lots réels, alerte stock partiel, coût unitaire). **Rappels qualité (fin de la gestion qualité)** : `quality-alerts` pur (température hors seuil = critique, relevé manquant du jour, nettoyage en retard, NC ouverte tous statuts, DLC expirée/à7 jours, tâche planning en retard ; tri critique→alerte→attention) +8 tests, panneau affiché sur le module Qualité pour **tous les rôles** (écriture restreinte). Les autres modules restent en lecture seule ou en démo locale.
- Pour essayer l'interface sans accès réseau, une **démo locale explicite** est disponible uniquement en développement : ajouter `PATISGEST_DEMO_MODE=true` et une valeur aléatoire d'au moins 32 caractères à `PATISGEST_DEMO_SECRET` dans `.env.local`. Les boutons de démo ne créent pas de session Supabase. Les opérations et données sont conservées uniquement dans le stockage local du navigateur, sans synchronisation. Tous les profils de démo partagent les mêmes données sur un navigateur ; cela ne constitue pas une sécurité métier.
- Démo : création d'articles, réception de lots, commandes fournisseurs à une ligne avec réceptions partielles, calcul FEFO et simulation de vente. Les recettes permettent de créer plusieurs fiches et d'ajouter des versions immuables (ingrédients de type matière, sans sous-recettes ni conversions d'unités). Coût HT et marge estimés avec le prix du premier lot FEFO actuel, la main-d’œuvre chargée, le parage, la cuisson et les frais ; il ne s'agit pas d'un coût historique figé.
- Démo : ordres de fabrication pour les recettes locales avec version active figée à la planification, lancement, consommation FEFO, alerte de manque et validation partielle ou totale. Comme dans le prototype, les besoins sont calculés sur le rendement brut ; le coût de lot est basé sur la quantité prévue et reste indicatif. En cas de manque ou de coût incomplet, le coût du lot produit est marqué incomplet et ce marqueur est transmis aux transferts et productions suivantes.
- Démo : transferts FEFO entre laboratoire et boutique, conservant numéro, DLC, congélation et coût. Un stock insuffisant bloque le transfert pour éviter la création fictive de stock. Les lots périmés ne sont pas automatiquement exclus, conformément au prototype ; ne pas utiliser la démo pour des produits réels.
- Démo : import Z depuis la caisse Boutique, format strict `code;quantité;prix HT` (séparateur `;`, sans en-tête), aperçu puis validation complète avant import. Un identifiant date/caisse/numéro identique est refusé ; un même total HT le même jour exige une confirmation car il peut s'agir d'un autre Z. L'import crée des ventes simulées et déduit les lots FEFO du stock actuel ; la date historique du Z ne reconstitue pas le stock passé et les mouvements sont datés du jour d'import. Les manques sont signalés, la clôture reste manuelle, les totaux TTC sont indicatifs et aucun paiement réel n'est effectué.
- Clôture déclarative à six flux **réelle** (RPC + révisions) : multi-produits et multi-sites, avec taux de perte (jeté + casse) / fabriqué, estimations HT fondées sur le prix de vente figé, et corrections conservées sous forme de révisions. Les unités différentes ne sont pas additionnées pour le taux global. Les flux ne sont pas rapprochés automatiquement de la caisse et ne modifient pas les stocks.
- Registre HACCP **réel** (écritures RLS) : températures avec seuil saisi, nettoyage et non-conformités liées ou non à un lot ; clôture avec action corrective et historique conservé. Une action corrective est requise pour clôturer une non-conformité et l'historique est conservé. Les seuils ne sont pas des recommandations réglementaires ; une alerte ne crée pas de non-conformité ni ne bloque un lot automatiquement. Ce registre local ne garantit aucune conformité sanitaire.
- Cake Design **réel** (RPC `creer_cake`/`evoluer_cake`) : devis avec options et rétroplanning J-3/J-1/J, versements avec historique, confirmation soumise à un acompte d'au moins 30 % (arrondi au centime supérieur), production, livraison après solde et annulation sans remboursement automatique. Les prix des options ne constituent pas un coût de revient complet. Il n'y a pas d'édition de devis, de paiement réel, de ticket, de TVA, de preuve d'acceptation des CGV, ni de synchronisation. Ne pas saisir de données personnelles réelles.
- Démo : traçabilité par identifiant de lot, liens connus achats → production → transferts → ventes, blocage avec motif et blocage facultatif des lots descendants connus. Une production déjà lancée crée un lot bloqué si un de ses lots consommés est bloqué. Le déblocage n'est pas propagé. Les ventes anciennes ne sont reliées que si leur mouvement porte l'identifiant exact ; les transferts anciens sans origine structurée ne sont pas déduits du seul numéro de lot. Ces limites sont signalées dans l'interface. Aucun rappel, notification ou retrait réel n'est effectué : ce module est une simulation, pas un système de sécurité sanitaire.
- Planning : **écriture réelle des tâches** (RLS) avec bascule « fait » ; capacité journalière et alerte de surcharge restent démonstratives. Date prévue pour chaque nouvel OF, tâches liées facultativement à un OF. Les besoins cumulés jusqu'à la date choisie utilisent les snapshots des OF planifiés non lancés et le stock actuel non bloqué du labo. Aucune réservation, commande ou réception future n'est prise en compte ; les anciens OF sans date sont exclus jusqu'à leur datation. Les lots périmés ne sont pas exclus.
- Démo : simulation HT sur la version active d'une recette, avec variation appliquée uniquement aux matières, frais constants, marge sur prix et coefficients. Elle utilise le premier prix FEFO courant et reste indicative ; les prix manquants ou incomplets empêchent l'affichage du résultat. Elle ne modifie aucun prix.
- Les données des anciennes sessions locales sont migrées à la lecture. Ce stockage n'est ni synchronisé ni protégé contre les modifications concurrentes dans plusieurs onglets.
- Tests : `npm run typecheck`, `npm run lint`, `npm test` (120 tests unitaires, Node 22 ou supérieur pour le test TypeScript natif), `npm run test:smoke` (6 tests HTTP : redirections non authentifiées, connexion de démonstration par server action, cookie forgé rejeté, 13 modules, 404, déconnexion avec effacement du cookie), `npm run build` (build de production).
